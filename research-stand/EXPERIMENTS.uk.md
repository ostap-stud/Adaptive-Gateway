# Досліди з автоматичним керуванням API

Ця інструкція задає втручання, контроль і спосіб фіксувати результат. Для порівняння часу між прогонами залишайте незмінними інтервали Eureka, Manager і Gateway, обладнання, число екземплярів та спосіб запуску. Приймальний тест прискорює інтервали й працює на інших портах. Його час запуску не є вимірюванням продуктивності.

## Перед початком

- Виконайте [локальне налаштування](README.md). Для першого досліду підготуйте окрему порожню інфраструктурну БД. Старий запис `catalog-service` перетворює первинне підключення на повторну синхронізацію. Автоматизована перевірка сама створює нові тимчасові БД.
- Підготуйте адміністратора, звичайного користувача з JWT та тестову роль, наприклад `ROLE_COMMERCE_READER`. Адмінпанель працює з обліковим записом `ROLE_INFRA_ADMIN`. Поведінку бізнес-операції перевіряйте окремо від імені гостя й звичайного користувача.
- Увімкніть потрібний режим на екрані **Adaptive**. Ручний цикл охоплює всі допущені сервіси. Якщо панель повідомляє про зайнятий цикл, дочекайтеся його завершення. За базового локального запуску Manager стартує у APPLY/DISCOVERY.
- Профіль змінюйте лише для **Research - catalog-service** у полі **Program arguments**. Наприклад, введіть `--spring.profiles.active=expanded`, зупиніть попередній екземпляр і запустіть той самий застосунок. За один раз використовуйте один із наведених профілів. Inventory та Order продовжують роботу. Профіль можна так само передати після імені JAR.

| Профіль Catalog | Реальна операція GET /catalog-service/selection | Декларація |
|---|---|---|
| Без аргументу або `default` | Відсутня | Відсутня у валідній специфікації |
| `expanded` | Присутня | PUBLIC |
| `authenticated` | Присутня | AUTHENTICATED |
| `permission` | Присутня | PERMISSION, `catalog.selection` |
| `docs-off` | Базовий каталог працює, OpenAPI недоступна | Eureka вказує на звичайний шлях документації |

Для кожного досліду збережіть час дії, стан Eureka, `observedAt`, `candidate.specHash`, результат `sync`, версію конфігурації, ID і active операції, ефективну політику та фактичний HTTP-код. За потреби вимірюйте час до **першого правильного запиту через Gateway**, вказуючи частоту опитування. Якщо зміну спостерігали між двома опитуваннями, цей інтервал визначає точність. JWT, паролі й технічні ключі вилучайте зі знімків.

Адреси локального запуску: `http://localhost:8335/observations` показує останнє спостереження. На `http://localhost:8088` використовуйте `/swagger/services/catalog-service`, `/auth-service/admin/services`, `/auth-service/admin/services/catalog-service/operations` та `/auth-service/admin/routes`. Для адміністративних API передайте JWT адміністратора. Звичайний GET спостережень читає вже наявний результат. Для примусового циклу панель викликає `POST /auth-service/admin/adaptive/poll`.

## 1. Первинне підключення

Почніть з OBSERVE і порожньої конфігурації прикладних сервісів. Запустіть Catalog без профілю, Inventory та Order. В Eureka перевірте по одному UP-екземпляру й три metadata у кожного. У спостереженнях знайдіть candidate зі шляхами у просторі імен сервісу, методом і політикою кожної операції. Для Inventory статус `ANALYZED_WITH_BLOCKED_OPERATIONS` допустимий через два INTERNAL endpoints. Перевірте, що до APPLY сервіси ще не створені в Auth.

Перемкніть Manager у APPLY. Після публікації перевірте три записи AUTOMATIC, по одному згенерованому маршруту та **6/5/5** базових операцій відповідно для Catalog/Inventory/Order. Відкрийте публічний список товарів через Gateway, список документації в Swagger та сторінку Services у панелі. Збережіть ID операцій і версію кожного сервісу.

## 2. Додавання операції

За вихідного профілю `default` перевірте відсутність шляху selection в OpenAPI. Перезапустіть Catalog з `expanded`. Дочекайтеся нового хешу та застосованої конфігурації. У списку operations має з’явитися активний GET з новим ID. Гостьовий запит через Gateway має повернути 200 та вибірку товарів. Запишіть ID для дослідів 5 і 7.

## 3. Зміна політики

Перейдіть з `expanded` на `authenticated`. Після синхронізації повторіть той самий GET без токена і з JWT звичайного користувача. Очікувані коди — 401 та 200. Зіставте ID, оголошену й ефективну політики, новий хеш. Контрольний гостьовий GET /catalog-service/products залишається доступним.

## 4. Декларативний дозвіл

Запустіть `permission` без mapping для `catalog.selection`. Для користувача з чинним JWT очікується 403. У **Permissions** знайдіть декларацію з порожніми ролями. Створіть mapping на `ROLE_COMMERCE_READER`, залишивши тестового користувача без цієї ролі. Повторіть запит тим самим JWT — очікується 403. Додайте користувачу роль через **Users**. Повторіть запит — очікується 200. За відсутності JWT за чинного mapping очікується 401. Збережіть запис аудиту й стан **Permissions** на кожному кроці.

## 5. Видалення та повернення

За попередньо активної selection перейдіть на `default`. Переконайтеся, що специфікація читається з кодом 200, містить базові шляхи й не містить selection. Після APPLY очікуйте `active=false` для попереднього ID, через Gateway — 404. Поверніть `expanded`, дочекайтеся `active=true`, перевірте той самий ID й гостьовий 200.

## 6. Тимчасова недоступність

За активного `expanded` збережіть версію, ingress route й перелік operations. Зупиніть лише Catalog. Відмітьте окремо момент зупинки процесу та момент, коли Eureka перестала вважати його UP. Раптове завершення може залишити стару реєстрацію до закінчення lease. Дочекайтеся MISSING або NO_UP_INSTANCE та порівняйте збережені записи Auth. Поки backend недоступний, код бізнес-запиту залежить від стану кешів. Контрольний критерій — збереження конфігурації. Запустіть той самий профіль, перевірте відновлення GET та попередні ID.

## 7. Адміністративне перевизначення

З профілем `expanded` відкрийте selection на екрані **Operations** і додайте policy шару ADMIN з `accessType=BLOCKED`, звичайним пріоритетом і причиною досліду. Переконайтесь у відповіді 403 звичайному користувачу. Перейдіть на `authenticated`, дочекайтеся зміненого хешу та публікації. Для того самого ID перевірте нову OPENAPI policy, збережену ADMIN policy й 403 з чинним JWT. Видаліть експериментальну ADMIN policy з причиною. Контроль — 401 для гостя та 200 для користувача.

## 8. Недоступна специфікація

Збережіть версію, ID й active всіх операцій у профілі `authenticated`. Перезапустіть Catalog з `docs-off`. Напряму перевірте 200 на `http://localhost:8911/catalog-service/products` та 404 на `/catalog-service/v3/api-docs` того самого порту. Дочекайтеся `OBSERVATION_FAILED`. Зіставте версію та operations у БД через адміністративний API. Мають зберегтися попередні записи. Відновіть `authenticated` і перевірте стан ANALYZED та автентифікований GET selection через Gateway. У цьому досліді навмисно відтворено відмову отримання документа.

## Форма фіксації спостереження

| Дослід / повтор | Початковий профіль → новий | Режим | Час втручання | Перше спостереження / статус | Хеш і версія до → після | ID / active | HTTP-коди гість / JWT | Час першої очікуваної відповіді | Примітка |
|---|---|---|---|---|---|---|---|---|---|
| | | | | | | | | | |

Для чистого повтору зніміть додану ADMIN policy, відновіть початковий mapping та роль тестового користувача, поверніть базовий профіль Catalog. Щоб повторити саме первинне підключення, використовуйте новий ізольований приймальний прогін. Історичні записи, вимірювання та конфігурацію робочої БД ці експерименти не потребують видаляти.
