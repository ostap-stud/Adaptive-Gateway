**4.3.** Початок відліку — приймання спостерігачем відповіді Eureka HTTP 204 на справжній запит реєстрації нової JVM Catalog. Кожен повтор отримав новий ідентифікатор екземпляра. Перед запуском підтверджено відсутність Catalog у Eureka, HTTP 404 для конфігурації в Auth та HTTP 404 для читання через Gateway. Роль запису вже прив’язана. Завершення — відповідь останньої перевірки спільного сценарію через Gateway. Медіана часу до першого успішного читання списку становила 2104,28 мс. Інтервал перед читанням Auth охоплює аналіз контракту, передавання даних і планування потоків. Внутрішні початок та кінець аналізу окремо недоступні. POST оновлення входить до синхронізації. Підсумовування цих відрізків дало б подвійний облік. Фактичну готовність підтверджено відповідями бізнес-API.

**4.4. Архівна серія.** Перед кожним підключенням обидва варіанти мали ті самі облікові записи, роль, готові JWT, відсутній маршрут і порожню прив’язку `catalog.write`. Для MANUAL спостерігач працював у режимі OBSERVE, для AUTOMATIC — APPLY з допуском DISCOVERY. Режим обрано до реєстрації. Порядок двох способів у парах чергувався. Медіана парних різниць «AUTOMATIC мінус MANUAL» становила 526,99 мс. В обох випадках час відраховано від такої самої відповіді Eureka до завершення однакової послідовності бізнес-перевірок.

Користувач із роллю читав список товарів, категорії та добірку, створював товар, читав його за ID, змінював ціну й деактивував. Завершальне читання деактивованого товару повертало 404. Запис гостя та користувача без ролі відхилено в обох варіантах. MANUAL вимагав створити сервіс, створити маршрут із роллю та оновити Gateway. В AUTOMATIC адміністратор прив’язав роль до дозволу `catalog.write`, а Manager створив маршрут GENERATED і сім API Operations. За часовими позначками окремих дій медіана суми тривалостей адміністративних HTTP-запитів становила 82,29 мс для MANUAL і 36,49 мс для AUTOMATIC. Кожен виклик, що змінює конфігурацію або публікує її, зараховано як одну дію.

Ручний варіант використовував один захищений маршрут із роллю на весь Catalog. Цей маршрут вимагає автентифікації навіть для читання. Різні набори ролей за шляхом або HTTP-методом у MANUAL потребують окремих маршрутів із відповідними предикатами. У GENERATED-маршруті контракт розрізняє публічні операції читання та окремі операції запису з дозволом. Спільний критерій порівняння — працездатність каталогу для уповноваженого користувача та заборона неуповноваженого запису. Гостьове читання оцінено додатково. Час включає очікування реєстру, застосування та виконання контрольних запитів. REST-виклики автоматизовано. Облік дій не охоплює роботу людини, підготовку контракту, створення спільних облікових записів або кількість внутрішніх викликів Manager.

**4.5.** В одному прогрітому Manager вимкнено періодичний запуск. Для кожного повтору один синхронний адміністративний запит запускав повний цикл огляду трьох прикладних сервісів. Межі — від відправлення запиту до отримання та декодування відповіді. Пауза планувальника, підготовка контракту і контрольні бізнес-запити поза цими межами. На кожній зміні чергувались два зняті з Catalog контракти з PUBLIC та AUTHENTICATED для добірки. Порядок сценаріїв у парах чергувався. HTTP-запити до добірки виконувались через справжній Gateway.

У 20 циклах без змін усі три сервіси повернули SKIP/UNCHANGED. Зафіксовано 0 запитів зміни від Manager до Auth і 0 запитів публікації від Auth до Gateway. Збіглися відбитки конфігурацій, версії та кількість записів журналу адаптації до і після кожного циклу. У 20 циклах зі зміною зафіксовано 20 синхронізацій і 20 публікацій. Кожна зміна додала одну версію й одну подію, а Gateway виконав нову політику. Ці перевірки охоплюють прикладні записи й публікацію. Фізичні записи PostgreSQL та внутрішні звернення кешу окремо не вимірювалися.
