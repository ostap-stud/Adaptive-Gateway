### Запуск у Windows

1. У локальній копії Adaptive Gateway потрібні зібрані JAR чотирьох інфраструктурних модулів і трьох застосунків стенду. За потреби виконайте з кореня `mvn package` та `mvn -f research-stand/pom.xml package` або відповідні цілі Maven в IntelliJ IDEA. Кожний модуль повинен мати один виконуваний JAR у своєму `target`.
2. Потрібні JDK 21, Python 3.10+ і серверні програми PostgreSQL (`initdb`, `postgres`, `pg_ctl`, `pg_isready`, `psql`). Постійний сервер PostgreSQL можна залишити у звичному стані. Для побудови рисунків у Windows використовується шрифт Arial. З кореня проєкту виконайте в PowerShell:

```powershell
py -3 -m venv "$env:TEMP\adaptive-study-venv"
$studyPython = "$env:TEMP\adaptive-study-venv\Scripts\python.exe"
& $studyPython -m pip install -r research-stand/experiments/requirements.txt
& $studyPython research-stand/experiments/run.py --java "$env:JAVA_HOME\bin\java.exe" --pg-bin "C:\Program Files\PostgreSQL\18\bin"
```

За потреби передайте повний шлях до JDK замість `JAVA_HOME`. Вимірювання і створення CSV потребують лише стандартної бібліотеки Python. Пакети з `requirements.txt` використовуються для рисунків. Для перевірки одного розділу додайте, наприклад, `--sections 4.3 --timing 2`. Для повтору 4.6 можна задати `--sections 4.6 --intervals 1 3 5 10 --window-s 24 --windows 10`. Повний набір параметрів показує `--help`.

3. Скрипт створить каталог `results/<час UTC>`. Параметр `--output` змінює місце збереження. Для повторної побудови таблиць і рисунків без запуску JVM виконайте `summarize.py` тим самим Python, передавши шлях до конкретного каталогу результатів.
4. Огляд відкривається у `tables.uk.md`. Для роботи з даними використовуйте `statistics.csv`, `checks.csv`, `pairs.csv`, `paired_statistics.csv` і `raw.csv`. Рисунки збережено в SVG та PNG. `raw.jsonl` доповнюється після кожного повтору й містить усі HTTP-проби. `conditions.json` зберігає параметри, версії, коміт і SHA-256 JAR та специфікацій. `control-events.json` містить часові позначки на контрольних HTTP-з’єднаннях. Виняток завершує серію, залишає рядок невдалого повтору, статус і діагностику. Перевірте статус `complete`, перш ніж використовувати серію як повну.

Для незалежної перевірки завершеного прогону виконайте `audit.py` тим самим Python із шляхом до каталогу результатів. Скрипт читає збережені дані та не запускає стенд.

### Ізоляція та контроль зміни

Скрипт перевіряє вільні порти, створює в новому тимчасовому каталозі окремий кластер PostgreSQL з випадковим паролем, дві БД і власні JVM. Усі адреси — loopback. Внутрішній PostgreSQL за замовчуванням слухає порт 39546; інші порти задано в `observers.py` й експортовано в `conditions.json`. У разі конфлікту портів прогін припиняється. Для завершення використовуються дескриптори запущених дочірніх процесів та шлях новоствореного кластера. Поточні дані користувача, Eureka і реєстрації його робочого стенду у вимірюваннях не використовуються.

Перед вимірюваннями той самий Catalog JAR послідовно запускається з профілями `default`, `authenticated`, `permission`, `expanded`. Клієнт отримує справжні JSON-документи й перевіряє оголошення selection. Під час серій працює один зареєстрований Catalog у профілі expanded, а також Order й Inventory. Сервер вимірювань перемикає збережений документ атомарно. Для Manager він пересилає відповідь справжньої Eureka, підставляючи в копії відповіді порт читання документа Catalog. Інші дані реєстру й документи решти сервісів надходять від справжніх компонентів. Запити синхронізації пересилаються в справжній Auth. Gateway використовує оригінальну Eureka і звертається безпосередньо до живого Catalog.

Така постановка вимірює реакцію **на зміну оголошеного контракту при готовому backend**. Під час видалення шлях selection продовжує існувати на backend, тому 404 через Gateway справді перевіряє деактивацію операції. Час запуску JVM, прогрів і вибір backend під час rolling deployment виходять за межі цієї оцінки. Додаткових прикладних мікросервісів немає.

|---|---|---|
| 4.3 | Цикл `default → expanded → authenticated → default`. Перед втручанням перевіряються стан Auth і вихідні відповіді. Для кожного переходу час відраховується після успішного контрольного GET нового документа. Паралельно вимірюється затримка цієї зміни. Перед новою серією перезапускається лише власний Manager з новим параметром запуску. | Паузи 1, 3, 5, 10 с; по 3 вікна по 24 с. | 4.2 | Додавання, посилення доступу, PERMISSION з відсутнім та налаштованим mapping, вилучення та повторна активація. Перевіряються ID, ознака active, фактичні HTTP-коди, унікальність операцій і шарів політик. | 5 циклів, 4 перевірені переходи в кожному. |
| 4.4 | Попарно відтворюється обмеження PUBLIC → AUTHENTICATED та повернення публічного доступу. В обох способах публікується однаковий документ. У ручному плечі Manager працює в OBSERVE, адміністратор виконує PUT/DELETE наявної ADMIN policy через REST Auth. В адаптивному — APPLY, зміни виконує Manager. Порядок плечей чергується між парами. | 10 пар для кожного напряму. |
| 4.5 | Повтор того самого PUT та requestId; справжня зміна версії між читанням і PUT (очікується 409); збереження ADMIN/BLOCKED; HTTP 503 при читанні OpenAPI; зупинка власної Eureka JVM, щонайменше дві спроби читання й повторна реєстрація трьох сервісів; зупинка власної Gateway JVM та відновлення того самого FAILED_REFRESH за requestId і версією. | По 5 для 6 перевірок. |

У 4.4 оцінюється час виконання підготовленої зміни. Клієнт уже має JWT адміністратора й ID операції. У лічильник входять записувальні REST-запити адміністратора після публікації документа. Вхід, вибір режиму, підготовка базового стану й контрольне читання спільні для постановки та винесені за межі вимірювання. Адміністративний запит і спостереження за Gateway виконуються паралельно. Це порівняння вартості виконання однакового рішення про доступ. Час, який людина витрачає на виявлення зміни, вибір політики та роботу в UI, тут не вимірюється.

### Часові позначки та похибка

- Усі інтервали обчислюються в одному процесі за `perf_counter_ns()`. UTC використовується для ідентифікації прогонів. `confirmed_ns` — кінець отримання й читання правильної специфікації. Перевіряється SHA-256. Різницю між перемиканням і підтвердженням збережено в `confirmation_roundtrip_ms`. Якщо Manager встиг прочитати документ у цьому проміжку, відносна позначка читання може бути від’ємною.
- `manager_fetch_ms` — початок першого отримання нової версії Manager. `sync_start_ms` та `sync_response_ms` — межі реального HTTP-запиту публікації, пов’язаного з подією Auth за requestId. `sync_rtt_ms` — його тривалість у точці пересилання, включно з діями Auth і перевіркою Gateway. Ці показники не ізолюють час запису SQL чи внутрішнього оновлення кешу. Snapshot Manager публікується після обходу сервісів. `detected_at` і `persisted_at` у міграції 004 обидва отримують `now()` тієї самої транзакції.
- `latency_ms` — час до завершення першої правильної **пари** послідовних відповідей на GET selection (гість, звичайний користувач із JWT). Для 200 перевіряється також структура результату. Проби стартують за сіткою 100 мс. Зайнятий слот пропускається. Для уточнення меж використовуйте фактичні початок і кінець кожної пари з `probes`. Це верхня спостережена межа часу до правильної поведінки. Дискретність проб, тривалість HTTP, планувальник Windows і додаткові переходи в контурі вимірювання впливають на точність. Спостережена зміна доступу може випереджати відповідь Auth про підтвердження публікації.
- Параметр Manager є **fixed delay** після завершення циклу. Тому кількість циклів за 24 с залежить також від тривалості обходу. Для 4.6 записуються часові зміщення всіх початків циклів, межі вікна та факт досягнення цільової поведінки в ньому. У 4.3 і 4.6 фазу втручання варіює відтворювана випадкова пауза. Це повтори на одному прогрітому стенді. Вони не дають оцінки багатовузлового розгортання або міжмашинної варіації.
- Для відмов Eureka та Gateway у 4.5 зупиняються справжні JVM цього прогону. Під час зупинки Eureka додатково публікується зміна документа. Після нового запуску перевіряються повторна поява всіх трьох застосунків і застосування відкладеної зміни. Код 0 у сирих даних позначає відсутність HTTP-відповіді на транспортному рівні.
- Зведення рахує успішні й невдалі повтори окремо. Часові статистики містять лише завершені коректні повтори. SD — вибіркове, знаменник `n−1`. P95 — елемент впорядкованої вибірки з номером `ceil(0,95·n)`, обчислюється за `n ≥ 20`. Для 4.4 окремо подано попарну різницю Manager − REST. На діаграмі розмаху 4.3 межі прямокутника — Q1 і Q3, риска — медіана. Вуса доходять до крайніх фактичних значень у межах 1,5 міжквартильного розмаху від квартилів. Спостереження поза цими межами позначаються точками. У 4.4 висота стовпчика відповідає медіані, відрізок — Q1–Q3. На рисунках 4.6 точки — медіани для досліджених пауз. Відрізки показують Q1–Q3 для затримки і мінімум–максимум для кількості циклів. Квартилі обчислено лінійною інтерполяцією між сусідніми порядковими статистиками.

### Підготовка рисунків і таблиць для МКР

Для 4.3 та 4.4 використано повний початковий прогін A. Для 4.6 обрано окремий прогін B з десятьма вікнами на паузу. Наведені команди читають збережені дані й виконуються з каталогу `research-stand/experiments` після встановлення пакетів з `requirements.txt`. Змінна `$studyPython` вказує на Python з інструкції вище.

```powershell
$runA = 'results/20261126T013026_133250Z'
$runB = 'results/20261126T034807_763709Z'
& $studyPython -B figures.py $runA --sections 4.3 4.4
& $studyPython -B figures.py $runB --sections 4.6
& $studyPython -B publication_tables.py $runA $runB
```

PNG для друку має роздільність 300 dpi. Поруч із кожним новим рисунком лежать SVG та CSV з вихідними груповими статистиками й ідентифікатором прогону. У таблицях наведено округлені значення, побудова рисунків використовує точність сирих вимірювань.
